Sometimes a WebView host needs the page to see a safe area the device does not
have. A kiosk view, a video player that should ignore the home indicator, a test
harness that wants deterministic insets. You need `env(safe-area-inset-bottom)`
to return `0px` so the page stops reserving space for a home bar that isn't
there.

Both platforms let you do it. The mechanisms are completely different, and each
fails silently. iOS additionally has a WebKit bug that makes a working override
look broken.

## Before and after

Both platforms, same page, same requested insets. Overrides requested were
`top 150, right 40, bottom 180, left 40`.

`41 0 0 0` → `77 21 92 21`. **Note the unit difference.** Android's override is
in *physical pixels* and CSS sees the result divided by `dpr` (1.96 here:
150/1.96 ≈ 77). iOS's override is in *points*, which already are CSS pixels, so
`150` in, `150px` out. If you port an override value between platforms you must
multiply by `dpr` on the Android side.

## Android: the mechanism

Android WebView computes the page's safe-area insets inside an internal
`AwContents` view, from the `WindowInsets` that reach it:

```java
int insetTypes = displayCutout() | systemBars();
Insets safeArea = toWindowInsetsCompat(insets).getInsets(insetTypes);
```

So the only lever is the insets themselves. Subclass `WebView` and override
`onApplyWindowInsets`:

```java
@Override
public WindowInsets onApplyWindowInsets(WindowInsets insets) {
    if (!hasInsetOverride() || Build.VERSION.SDK_INT < Build.VERSION_CODES.R) {
        return super.onApplyWindowInsets(insets);
    }
    return super.onApplyWindowInsets(applyOverrides(insets));
}

private WindowInsets applyOverrides(WindowInsets insets) {
    WindowInsets.Builder builder = new WindowInsets.Builder(insets);
    int[] types = {
        WindowInsets.Type.statusBars(),
        WindowInsets.Type.navigationBars(),
        WindowInsets.Type.captionBar(),
        WindowInsets.Type.displayCutout(),
    };
    for (int type : types) {
        Insets current = insets.getInsets(type);
        builder.setInsets(type, Insets.of(
            leftOverride   != null ? leftOverride   : current.left,
            topOverride    != null ? topOverride    : current.top,
            rightOverride  != null ? rightOverride  : current.right,
            bottomOverride != null ? bottomOverride : current.bottom));
    }
    return builder.build();
}
```

Condensed from
[`InsetAwareWebView.java`](https://github.com/amoshydra/android-webview-launcher/blob/63980eecfd92f33f9ca698cdf0d7e7b10cdee591/app/src/main/java/com/amoshydra/androidapp/InsetAwareWebView.java#L70-L100);
that class is 101 lines and this is all of it that matters.

One line in that excerpt is out of date. The gate reads `VERSION_CODES.R`, which
is API 30, and the floor is really 31, for the dispatch-order reason given below.

Three things that each cost someone a day:

**`setOnApplyWindowInsetsListener` cannot do this.** The callback returns a
boolean, and the AndroidX compat wrapper maps `!= null` onto that boolean, so a
rebuilt `WindowInsetsCompat` never reaches the WebView. Overriding
`onApplyWindowInsets` works because `ViewGroup.dispatchApplyWindowInsets` passes
its return value down to children, and `AwContents` is one.

**Every edge must be set on every type in the mask.** `getInsets(mask)` returns
the per-edge *maximum* across the mask. Overriding only `navigationBars()` leaves
a non-zero bottom wherever a display cutout also contributes one.

**Requires API 31+**, and only works in edge-to-edge mode, because otherwise the
framework consumes the insets before the WebView sees them. In that mode the
status bar stays visible but transparent; hiding it zeroes the `statusBars()`
inset, which leaves the page with a top inset of zero and hides the cutout from
it.

The floor is 31 rather than 30 because of who gets to consume the dispatch. On
API 28 to 30 the WebView provider installs its own `OnApplyWindowInsetsListener`
on the container view that wraps your `WebView`, and Android stops delivering
insets as soon as a listener consumes them, so the `onApplyWindowInsets` you
overrode is never reached. From API 31 the provider hooks `onApplyWindowInsets`
on a view inside the WebView instead, which sits below yours, so yours runs
first. There is no API 28 to 30 device in the matrix below, so that part rests
on the code path rather than on a measurement.

## iOS: the mechanism

Much smaller, because there is no interception layer to hook. WebKit derives the
page's `env(safe-area-inset-*)` from the **receiving view's** `safeAreaInsets`, so
overriding that one getter is the whole mechanism:

```swift
final class InsetOverrideWebView: WKWebView {
    /// Per-edge overrides in points. `nil` leaves that edge at the real system value.
    var insetOverride = InsetOverride() {
        didSet {
            guard insetOverride != oldValue else { return }
            // UIKit memoises safe-area geometry per layout pass, so the override is
            // only re-read once something invalidates that cache.
            setNeedsLayout()
            invalidateIntrinsicContentSize()
        }
    }

    override var safeAreaInsets: UIEdgeInsets {
        insetOverride.applying(to: super.safeAreaInsets)
    }
}

struct InsetOverride: Equatable {
    var top: CGFloat?
    var right: CGFloat?
    var bottom: CGFloat?
    var left: CGFloat?

    var isEmpty: Bool { top == nil && right == nil && bottom == nil && left == nil }

    func applying(to base: UIEdgeInsets) -> UIEdgeInsets {
        UIEdgeInsets(
            top: top ?? base.top,
            left: left ?? base.left,
            bottom: bottom ?? base.bottom,
            right: right ?? base.right
        )
    }

    static func parseEdges(top: String, right: String,
                           bottom: String, left: String) -> InsetOverride {
        InsetOverride(top: parse(top), right: parse(right),
                      bottom: parse(bottom), left: parse(left))
    }

    /// Blank = leave at the real system value. Non-numeric is treated the same
    /// way rather than silently becoming 0.
    private static func parse(_ raw: String) -> CGFloat? {
        let trimmed = raw.trimmingCharacters(in: .whitespacesAndNewlines)
        guard !trimmed.isEmpty, let value = Double(trimmed), value >= 0 else { return nil }
        return CGFloat(value)
    }
}
```

Condensed from
[`InsetOverrideWebView.swift`](https://github.com/amoshydra/ios-webview-launcher/blob/4f48bd40f7e3f08d7cdb5219ee51a8aaf8822957/Sources/InsetOverrideWebView.swift#L17-L58).
The comment above `insetOverride` is the same one, and it is worth reading in
place: UIKit memoises safe-area geometry per layout pass, so an override that is
not read after something invalidates that cache silently does nothing.

`nil` per edge means "use the real system value". Values are deliberately not
clamped, so a value larger than the real inset pushes content further in, which
is the point when you're inflating a fake inset.

Verified per-edge independence on iOS 27.0, with only `top` overridden:

| Config | `webView.safeAreaInsets` | page `env()` |
| --- | --- | --- |
| all blank | `t:62 r:0 b:34 l:0` | `62px 0px 34px 0px` |
| `top=111` only | `t:111 r:0 b:34 l:0` | `111px 0px 34px 0px` |
| `111/44/222/33` | `t:111 r:44 b:222 l:33` | `111px 44px 222px 33px` |

Row 1 is the sanity check that the pipeline reads real data, since `62px` is exactly
`window.safeAreaInsets.top`. Row 2 shows the other three edges falling through to
genuine system values rather than being zeroed. Row 3 sets all four and gets all
four back.

## Side by side

| | Android | iOS |
|---|---|---|
| Hook | `View.onApplyWindowInsets` | `WKWebView.safeAreaInsets` getter |
| Override units | Physical px | Points (= CSS px) |
| `viewport-fit=cover` needed | No (WebView M136+) | **Yes** |
| CSS injection needed | No | No |
| Minimum version | API 31 | iOS 11 |
| Extra requirement | Edge-to-edge, or insets are consumed first | `contentInsetAdjustmentBehavior = .never` |
| Cost of skipping that requirement | Insets never reach the page | Page reads them, but in a viewport already shrunk by them |
| Per-edge `nil` fall-through | Yes | Yes |
| Change while the page is loaded | Yes, after an insets dispatch | Yes, assign the property |
| Bottom edge with the keyboard open | Reclaimed by the IME | Not measured |
| Easy to get wrong | Must set all edges on all types in the mask | Values arrive non-deterministically (below) |

## Three iOS conditions

Each one fails in its own way, and only the first fails loudly. Miss
`viewport-fit=cover` and every edge reads `0px` with no error. Miss the
adjustment behaviour and the page reports the right numbers from the wrong
viewport, which is harder to catch than zeros because nothing looks broken until
the layout is compared against something. The third one, ordering, fails by
leaving the page briefly correct against the wrong insets.

**1. `viewport-fit=cover` in the document.**

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover" />
```

WebKit reports `0` for every `env(safe-area-inset-*)` without it, and no native
change can alter that. It's the same rule Safari follows. This is the one real
behavioural gap versus Android, whose WebView M136+ populates the values from
`WindowInsets` with no opt-in. **The page must cooperate.**

**2. `contentInsetAdjustmentBehavior = .never`.**

```swift
webView.scrollView.contentInsetAdjustmentBehavior = .never
```

Any other value lets UIKit inset the scroll view by the safe area, and the page
ends up inside an already-inset viewport. That is the failure, and it is not
zeros. Measured on iOS 18.6 and again on 26.5, iPhone 17 Pro, override applied in
`makeUIView`, sampled every animation frame. `env()` is identical in every row,
so the readout will not warn you:

| `contentInsetAdjustmentBehavior` | `adjustedContentInset` | Page `env()` | `clientWidth x clientHeight` |
| --- | --- | --- | --- |
| `.never` | `0 0 0 0` | `150 40 180 40` | `402 x 874` |
| `.automatic` | `150 0 180 0` | `150 40 180 40` | `402 x 544` |
| `.scrollableAxes` | `150 0 180 0` | `150 40 180 40` | `402 x 544` |
| `.always` | `150 40 180 40` | `150 40 180 40` | `322 x 544` |

The height arithmetic is the same in every row that insets: 874 minus the 150 top
and 180 bottom override is 544. Width only goes under `.always`, where 402 minus
the 40 left and 40 right is 322.

Neither of the middle two is a safe compromise. They keep the width and still cost
the page 330 points of height, which is the part a document is least likely to
notice has gone.

The consequence is a double inset. A page that pads its body by `env()` gets the
safe area applied twice, once by UIKit shrinking the layout viewport and once by
the page's own padding. The demo page's scroll range shows it: 797 under `.never`,
1286 under `.always`.

Straight from

**3. Set the override before the first layout pass**, in `makeUIView` and not from a
later callback. It is one of the first lines of
[`makeUIView`](https://github.com/amoshydra/ios-webview-launcher/blob/4f48bd40f7e3f08d7cdb5219ee51a8aaf8822957/Sources/WebViewScreen.swift#L122-L139),
and the Android host orders it the same way, before `setContentView` rather than
after.

Setting it late does not zero the reporting. It leaves the page laid out against
the real safe area until something invalidates the geometry UIKit has memoised,
and then it converges on the override without a reload. Same page, two runs, the
only difference being when the assignment happens:

| Override assigned | First reading | Then |
| --- | --- | --- |
| In `makeUIView`, before the first layout pass | `150 40 180 40` | stays there |
| 1.0s later, from a callback | `62 0 34 0` | `150 40 180 40` at 562 ms |

The 562 ms is the `didSet` reaching a layout pass. If you go looking for the
symptom the post used to promise, zeros, you will not find it: the page is
briefly correct against the wrong insets instead.

That is about the first value only. Changing the override later, with the page
already loaded, reaches the page on both platforms.

## Changing the override while the page is loaded

Both mechanisms can be re-applied after the page has loaded, and on every runtime
measured here the page followed without a reload. What changes is the extra step:
setting the value is no longer enough, because something has to make the platform
read it again.

On Android the override is applied inside `onApplyWindowInsets`, so a new value
does nothing until insets are dispatched again. Either call works:

```java
webView.setInsetOverride(top, right, bottom, left);
// then one of these
webView.dispatchApplyWindowInsets(webView.getRootWindowInsets());
webView.getRootView().requestApplyInsets();
```

Both produced the same numbers on the OnePlus and both reached the page on the
next animation frame. Prefer `requestApplyInsets()`: it travels the hierarchy the
way a real insets change does, so it cannot skip a parent that consumes them,
which is the same mechanism that puts the Android floor at API 31.

On iOS there is no dispatch to trigger. Assigning the property is the whole
update, because its `didSet` calls `setNeedsLayout()` and
`invalidateIntrinsicContentSize()`, which is what invalidates the safe-area
geometry UIKit has memoised.

Sampled every animation frame, so "second frame" means the frame after the first
one that drew:

| Runtime | Device | Correct after load | Live change seen by the page |
| --- | --- | --- | --- |
| 18.6 | iPhone 16 Pro | 847 ms, second frame | `150 40 180 40` to `300 80 360 80` |
| 26.5 | iPhone 17 Pro | 67 ms | `150 40 180 40` to `300 80 360 80` |
| 27.0 | iPhone 18 Pro Max | 165 ms | `150 40 180 40` to `300 80 360 80` |
| 27.1 | iPhone Duo | 276 ms | `150 40 180 40` to `300 80 360 80` |
| 27.2 | iPhone 18 Pro | 667 ms | `150 40 180 40` to `300 80 360 80` |
| Android 15 | OnePlus 6T, WebView 153 | 40 ms, second frame | `77 21 92 21` to `153 41 184 41` |

The Android row is the same two requests as the iOS rows, reported in CSS px
after the division by dpr.

Those are single runs, and the runtime is not the whole story: 18.6 gave 463 ms on
one simulator and 847 ms on another, which is the same non-determinism the sampled
table below records.

`nil` still means the real system value after a change, not only at load.
Requesting `300` on the top edge alone gave the page `300 0 34 0` on every runtime,
with the untouched bottom edge reporting its real 34pt.

Neither launcher exposes this today. Android reads its overrides once in
`onCreate` and the settings screen finishes by starting a second
`MainActivity`, which reloads the page; on iOS the values live in the settings
screen, so changing them means leaving the page. The useful shape is a test loop:
run one page and walk it through no inset, a home bar, a notch and back, rather
than relaunching with different intent extras each time. After changing a value,
confirm the page moved, because from the native side a change that never reached
the page looks exactly like one that did.

## The keyboard takes the bottom edge

While a text field has focus, Android hands the bottom of the screen to the IME
and the page's bottom inset goes to zero, whatever the host asked for. The page
below requested 180px, which is 92 CSS px at dpr 1.96, and the blue band is the
safe area it was given:

| Keyboard closed | Keyboard open |
| --- | --- |
| <img class="shot" src="/blog/posts/webview-safe-area-inset-override/keyboard-closed.webp" alt="A page reading 77 21 92 21, with a blue band along all four edges, above a text field" /> | <img class="shot" src="/blog/posts/webview-safe-area-inset-override/keyboard-open.webp" alt="The same page reading 77 21 0 21 with the keyboard up: the top, left and right bands are unchanged and the bottom band is gone" /> |

`77 21 92 21` becomes `77 21 0 21`, and the other three edges are untouched. The
override is still set throughout and the value returns when the IME closes, so
nothing reports a problem.

This matters most for the case this post is about. A kiosk page that inflates its
bottom inset to clear a home bar the device does not have loses exactly that
margin the moment an input takes focus. The keyboard really does occupy that
space, so read it as the platform handing the edge back rather than as the
override failing, and do not build a layout that needs the bottom inset to
survive a keyboard. iOS was not measured: raising the software keyboard needs
Simulator.app, which this run did not have.

## Reading what the page sees

The page's `env()` values are the only evidence that any of this worked, and the
obvious way to read them reports a working override as broken. Every table above
comes from a page that samples on a timer or on a frame rather than once. A
single read from the same pages at load would have reported zeros.

### A single read lands in the zero window

[WebKit bug 191872](https://bugs.webkit.org/show_bug.cgi?id=191872), open since
2018 and still open:

> These CSS variables are not available on the initial load of the app, or after
> the window load event, or the document DOMContentLoaded event. These CSS
> variables only seem to be available at some arbitrary time after the app is
> loaded.

A comment from 2023 notes the same on iOS 16, and that because it is
non-deterministic it is "very hard to work around manually". Measuring in
`webView(_:didFinish:)` lands inside exactly the window where the values are
guaranteed to be zero.

I hit this. My first test read once on `didFinish`, got `0px` on all four edges,
and I wrote it up as "the override does not work on iOS". It does work. Sampling
12 times over 6s and recording the history:

```text
label=edgeToEdge=true top=150.0 right=40.0 bottom=180.0 left=40.0
        | native webview=t:150 r:40 b:180 l:40 window=t:62 r:0 b:34 l:0
settled={"top":"150px","right":"40px","bottom":"180px","left":"40px"}
distinctReadings=2
history:
  [0] {"top":"0px","right":"0px","bottom":"0px","left":"0px"}
  [1] {"top":"150px","right":"40px","bottom":"180px","left":"40px"}
```

Reading `[0]`, which is what the single read returned, looks like total failure.

How many samples it takes is **not predictable**:

| Runtime | Device | Distinct readings |
| --- | --- | --- |
| 18.6 | iPhone 16 Pro | 2, zero then override |
| 26.5 | iPhone 17 Pro | 1, override immediately |
| 27.0 | iPhone 17 Pro | 2, zero then override |
| 27.0 | iPhone 18 Pro | 2, zero then override |
| 27.1 | iPhone Duo | 1 on the first run, 2 on a later one |

Twelve samples, half a second apart, starting at page finish. A count of 1 means
the very first sample was already correct.

The Duo is the row to read twice. The run behind this table found the override
already correct on its first sample. A later run, same device and same runtime,
read all four edges as zero first and needed the second sample. Identical
hardware and identical runtime, two answers, which is the argument for sampling
over time rather than for counting.

The same iPhone 17 Pro needed two samples on 27.0 and one on 26.5. Any test of
this has to sample over time; a single read is a coin flip.

Android reads zero at the same moments and recovers faster. On the OnePlus the
page reported `0 0 0 0` while its script ran, at the `load` event, and on the
first animation frame, then `77 21 92 21` on the second frame about 40 ms later.
So the rule is the same on both platforms and the reason differs. Android needs
one frame; iOS needs a wait that is not predictable.

### Resolving env() through a probe element

`env()` has no JavaScript API, so the only way to observe what a page sees is to
resolve it through a probe element and read the computed style:

```js
var p = document.createElement('div');
p.style.cssText = 'position:fixed;top:0;left:0;visibility:hidden;' +
  'padding-top:env(safe-area-inset-top,0px)' /* … */;
document.body.appendChild(p);
var cs = getComputedStyle(p);
cs.paddingTop; // "150px"
```

Sample it per animation frame rather than once. One read can land in the zero
window, and a per-frame sampler both avoids that and shows you when the value
arrived. That is how the runtime section above was measured.

This is the probe from
[`EnvProbe.readEnv`](https://github.com/amoshydra/ios-webview-launcher/blob/4f48bd40f7e3f08d7cdb5219ee51a8aaf8822957/Sources/EnvProbe.swift#L12-L31),
with the comment it carries explaining why the probe element exists at all: there
is no JS API for `env()`, so reading the value out of the page is the only honest
check.

Three guards make a reading trustworthy:

**Prove `env()` is supported.** Read it with a fallback. If
`env(safe-area-inset-top, 77px)` returns `77px`, `env()` is unsupported and every
other number is void. Reading `0px` proves it resolved to a genuine zero. Pick a
fallback no override is likely to produce, because a sentinel that collides with
a real value reports a working `env()` as unsupported. The `viewport-fit=cover`
half of that guard is
[`readViewportFit` in the same file](https://github.com/amoshydra/ios-webview-launcher/blob/4f48bd40f7e3f08d7cdb5219ee51a8aaf8822957/Sources/EnvProbe.swift#L33-L40).

**Capture the native value too**, so the two can be compared:

```swift
let safe = webView.safeAreaInsets           // t:150 r:40 b:180 l:40
let window = webView.window?.safeAreaInsets // t:62  r:0  b:34  l:0
```

If they diverge, the override never reached `env()`. If they agree and the page
still reads zero, the reading is what is wrong, not the override.

Agreement is necessary but not sufficient, and condition 2 is the case that proves
it. There, `safeAreaInsets` and `env()` matched exactly while the page was laid
out in the wrong viewport. So a check that only compares inset numbers passes on
a page that is visibly broken. Pair it with the geometry, which is the one reading
that caught it:

```js
[document.documentElement.clientWidth, document.documentElement.clientHeight];
// "402 x 874" under .never, "322 x 544" under .always, same override
```

### The SDK decides whether you get edge-to-edge at all

Everything above was captured with **Xcode 27.0**, and that is what the `871 × 669`
in the unfolded row is. It is not the real display size. The Duo's inner panel is
951 points wide, and an app built with the iOS 27.0 SDK does not get it: iOS gives
the app a window of 871 points and leaves the remaining 80 in a black rail, so the
page never learns the extra space exists.

The status bar is a vertical bar on the Duo, occupying a reserved region at the
outer edge. Whether an app may extend underneath it is decided by the SDK it is
built against, not by anything in the app:

| Built against | Outer display | Inner display |
| --- | --- | --- |
| Pre-iOS 27 SDK | Letterboxed | Letterboxed |
| iOS 27.0 SDK | Letterboxed | 871 of 951 points |
| **iOS 27.1 SDK** | **Edge to edge** | **Edge to edge** |

Same app, same code, same page, same pose — only the SDK differs. Each row is one
orientation, the 27.0 build on the left and the 27.1 build on the right:

| Pose | Xcode 27.0 — letterboxed | Xcode 27.1 — edge to edge |
| --- | --- | --- |

Read the readouts across each row. On the outer display in portrait the page goes
from `386 × 678` with insets `0 0 34 0` to `466 × 678` with `0 84 34 0`. On the
inner display in landscape it goes from `871 × 669` to the panel's full
`951 × 669`, again gaining an 84pt right inset. In portrait the inset moves to the
other edge: `669 × 871` with `0 0 34 0` becomes `669 × 951` with `82 0 34 0`, so the
status bar's reserved region follows the rotation, sitting along the top in
portrait and down one side in landscape.

That 34pt on a 27.0 build is the trap: it is the letterbox boundary being reported
as if it were a safe area, not a system inset. A 27.1 build reports 0 there and
instead gives a real 84pt for the status bar, which is the inset a page can
actually lay out against.

This matters for the override. The `left` and `right` insets it writes are
per-edge, so it still works either way — but on a 27.0 build it is writing into a
window the system already cropped, and any page compensating for
`env(safe-area-inset-right)` is compensating for a boundary that would not exist on
a 27.1 build. **For the Duo, use Xcode 27.1 or later.** Getting there is only
`DEVELOPER_DIR`:

```bash
DEVELOPER_DIR=/path/to/Xcode-27.1.app/Contents/Developer \
  xcodebuild -project WebViewLauncher.xcodeproj -scheme WebViewLauncher \
  -sdk iphonesimulator build CODE_SIGNING_ALLOWED=NO
```

Note that the *runtime* is not the *SDK*. A 27.1 simulator runtime is enough to
create the device and run on it, which is how the two SDKs can be compared on the
same pose, but the app still compiles against whatever SDK the selected Xcode
ships.

Two things fall out of that.
**No top inset, ever.** Compare the Pro models at `62 0 34 0`: the outer display
has no notch and, in the simulator, no status-bar inset, so the top is 0 in all
three states. A 150pt top override here is not restating an existing value the way
it is on a Pro, it is manufacturing an inset the hardware does not have, which is
the case where the override is most useful and hardest to test against real
hardware.

**The insets move with orientation and fold.** In portrait the whole 34pt is at
the bottom, for the home indicator. Rotate to landscape, or open the inner
display, and it splits: 34pt on each side, 20pt at the bottom. Anything that
hard-codes `env(safe-area-inset-bottom)` to size a footer is wrong in two of these
three states, and nothing in CSS warns you.

With `150 / 40 / 180 / 40` requested, the outer display reported exactly those
values back. Whether the very first sample already had them varies between
runs, which the timing table above records.
