Sometimes a WebView host needs to lie to the page about the safe area. A kiosk
view, a video player that should ignore the home indicator, a test harness that
wants deterministic insets. You need `env(safe-area-inset-bottom)` to return `0px`
so the page stops reserving space for a home bar that isn't there.

Both platforms let you do it. The mechanisms are completely different, and each
fails silently. iOS additionally has a WebKit bug that makes a working override
look broken.

`41 0 0 0` → `77 21 92 21`. **Note the unit difference.** Android's override is
in *physical pixels* and CSS sees the result divided by `dpr` (1.96 here:
150/1.96 ≈ 77). iOS's override is in *points*, which already are CSS pixels, so
`150` in, `150px` out. If you port an override value between platforms you must
multiply by `dpr` on the Android side.

## Android: the mechanism

Android WebView computes the page's safe-area insets inside an internal
`AwContents` view, from the `WindowInsets` that reach it:

```java
int insetTypes = displayCutout() | systemBars();
Insets safeArea = toWindowInsetsCompat(insets).getInsets(insetTypes);
```

So the only lever is the insets themselves. Subclass `WebView` and override
`onApplyWindowInsets`:

```java
@Override
public WindowInsets onApplyWindowInsets(WindowInsets insets) {
    if (!hasInsetOverride() || Build.VERSION.SDK_INT < Build.VERSION_CODES.R) {
        return super.onApplyWindowInsets(insets);
    }
    return super.onApplyWindowInsets(applyOverrides(insets));
}

private WindowInsets applyOverrides(WindowInsets insets) {
    WindowInsets.Builder builder = new WindowInsets.Builder(insets);
    int[] types = {
        WindowInsets.Type.statusBars(),
        WindowInsets.Type.navigationBars(),
        WindowInsets.Type.captionBar(),
        WindowInsets.Type.displayCutout(),
    };
    for (int type : types) {
        Insets current = insets.getInsets(type);
        builder.setInsets(type, Insets.of(
            leftOverride   != null ? leftOverride   : current.left,
            topOverride    != null ? topOverride    : current.top,
            rightOverride  != null ? rightOverride  : current.right,
            bottomOverride != null ? bottomOverride : current.bottom));
    }
    return builder.build();
}
```

Condensed from
[`InsetAwareWebView.java`](https://github.com/amoshydra/android-webview-launcher/blob/63980eecfd92f33f9ca698cdf0d7e7b10cdee591/app/src/main/java/com/amoshydra/androidapp/InsetAwareWebView.java#L70-L100);
that class is 101 lines and this is all of it that matters.

Three things that each cost someone a day:

**`setOnApplyWindowInsetsListener` cannot do this.** The callback returns a
boolean, and the AndroidX compat wrapper maps `!= null` onto that boolean, so a
rebuilt `WindowInsetsCompat` never reaches the WebView. Overriding
`onApplyWindowInsets` works because `ViewGroup.dispatchApplyWindowInsets` passes
its return value down to children, and `AwContents` is one.

**Every edge must be set on every type in the mask.** `getInsets(mask)` returns
the per-edge *maximum* across the mask. Overriding only `navigationBars()` leaves
a non-zero bottom wherever a display cutout also contributes one.

**Requires API 30+**, and only works in edge-to-edge mode — otherwise the
framework consumes the insets before the WebView sees them. In that mode the
status bar stays visible but transparent; hiding it zeroes the `statusBars()`
inset, which leaves the page with a top inset of zero and hides the cutout from
it.

## iOS: the mechanism

Much smaller, because there is no interception layer to hook. WebKit derives the
page's `env(safe-area-inset-*)` from the **receiving view's** `safeAreaInsets`, so
overriding that one getter is the whole mechanism:

```swift
final class InsetOverrideWebView: WKWebView {
    /// Per-edge overrides in points. `nil` leaves that edge at the real system value.
    var insetOverride = InsetOverride() {
        didSet {
            guard insetOverride != oldValue else { return }
            // UIKit memoises safe-area geometry per layout pass, so the override is
            // only re-read once something invalidates that cache.
            setNeedsLayout()
            invalidateIntrinsicContentSize()
        }
    }

    override var safeAreaInsets: UIEdgeInsets {
        insetOverride.applying(to: super.safeAreaInsets)
    }
}

struct InsetOverride: Equatable {
    var top: CGFloat?
    var right: CGFloat?
    var bottom: CGFloat?
    var left: CGFloat?

    var isEmpty: Bool { top == nil && right == nil && bottom == nil && left == nil }

    func applying(to base: UIEdgeInsets) -> UIEdgeInsets {
        UIEdgeInsets(
            top: top ?? base.top,
            left: left ?? base.left,
            bottom: bottom ?? base.bottom,
            right: right ?? base.right
        )
    }

    static func parseEdges(top: String, right: String,
                           bottom: String, left: String) -> InsetOverride {
        InsetOverride(top: parse(top), right: parse(right),
                      bottom: parse(bottom), left: parse(left))
    }

    /// Blank = leave at the real system value. Non-numeric is treated the same
    /// way rather than silently becoming 0.
    private static func parse(_ raw: String) -> CGFloat? {
        let trimmed = raw.trimmingCharacters(in: .whitespacesAndNewlines)
        guard !trimmed.isEmpty, let value = Double(trimmed), value >= 0 else { return nil }
        return CGFloat(value)
    }
}
```

Condensed from
[`InsetOverrideWebView.swift`](https://github.com/amoshydra/ios-webview-launcher/blob/4f48bd40f7e3f08d7cdb5219ee51a8aaf8822957/Sources/InsetOverrideWebView.swift#L17-L58).
The comment above `insetOverride` is the same one, and it is worth reading in
place: UIKit memoises safe-area geometry per layout pass, so an override that is
not read after something invalidates that cache silently does nothing.

`nil` per edge means "use the real system value". Values are deliberately not
clamped, so a value larger than the real inset pushes content further in — which
is the point when you're inflating a fake inset.

Verified per-edge independence on iOS 27.0, with only `top` overridden:

| Config | `webView.safeAreaInsets` | page `env()` |
| --- | --- | --- |
| all blank | `t:62 r:0 b:34 l:0` | `62px 0px 34px 0px` |
| `top=111` only | `t:111 r:0 b:34 l:0` | `111px 0px 34px 0px` |
| `111/44/222/33` | `t:111 r:44 b:222 l:33` | `111px 44px 222px 33px` |

Row 1 is the sanity check that the pipeline reads real data — `62px` is exactly
`window.safeAreaInsets.top`. Row 2 shows the other three edges falling through to
genuine system values rather than being zeroed.

## Three iOS conditions

Miss any one and all four edges read `0px` with no error.

**1. `viewport-fit=cover` in the document.**

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover" />
```

WebKit reports `0` for every `env(safe-area-inset-*)` without it, and no native
change can alter that — it's the same rule Safari follows. This is the one real
behavioural gap versus Android, whose WebView M136+ populates the values from
`WindowInsets` with no opt-in. **The page must cooperate.**

**2. `contentInsetAdjustmentBehavior = .never`.**

```swift
webView.scrollView.contentInsetAdjustmentBehavior = .never
```

Any other value lets UIKit inset the scroll view, which suppresses the page's
safe-area reporting entirely. Re-assert it in `updateUIView`, since a layout
change can reset it:

```swift
func updateUIView(_ webView: WKWebView, context: Context) {
    if let overridable = webView as? InsetOverrideWebView {
        overridable.insetOverride = insetOverride
    }
    webView.scrollView.contentInsetAdjustmentBehavior = .never
    // …
}
```

Straight from
[`WebViewScreen.swift`](https://github.com/amoshydra/ios-webview-launcher/blob/4f48bd40f7e3f08d7cdb5219ee51a8aaf8822957/Sources/WebViewScreen.swift#L141-L148).

**3. Set the override before the first layout pass** — in `makeUIView`, not from a
later callback. It is one of the first lines of
[`makeUIView`](https://github.com/amoshydra/ios-webview-launcher/blob/4f48bd40f7e3f08d7cdb5219ee51a8aaf8822957/Sources/WebViewScreen.swift#L122-L139),
and the Android host orders it the same way, before `setContentView` rather than
after.

## Do not measure this with a single read

[WebKit bug 191872](https://bugs.webkit.org/show_bug.cgi?id=191872) — open since
2018, still open:

> These CSS variables are not available on the initial load of the app, or after
> the window load event, or the document DOMContentLoaded event. These CSS
> variables only seem to be available at some arbitrary time after the app is
> loaded.

A comment from 2023 notes the same on iOS 16, and that because it is
non-deterministic it is "very hard to work around manually". Measuring in
`webView(_:didFinish:)` lands inside exactly the window where the values are
guaranteed to be zero.

I hit this. My first test read once on `didFinish`, got `0px` on all four edges,
and I wrote it up as "the override does not work on iOS". It does work. Sampling
12 times over 6s and recording the history:

```text
label=edgeToEdge=true top=150.0 right=40.0 bottom=180.0 left=40.0
        | native webview=t:150 r:40 b:180 l:40 window=t:62 r:0 b:34 l:0
settled={"top":"150px","right":"40px","bottom":"180px","left":"40px"}
distinctReadings=2
history:
  [0] {"top":"0px","right":"0px","bottom":"0px","left":"0px"}
  [1] {"top":"150px","right":"40px","bottom":"180px","left":"40px"}
```

Reading `[0]` — what the single read returned — looks like total failure.

How many samples it takes is **not predictable**:

| Runtime | Device | Distinct readings |
| --- | --- | --- |
| 18.6 | iPhone 16 Pro | 2 — zero, then override |
| 26.5 | iPhone 17 Pro | 1 — override immediately |
| 27.0 | iPhone 17 Pro | 2 — zero, then override |
| 27.0 | iPhone 18 Pro | 2 — zero, then override |
| 27.1 | iPhone Duo | 1 — override immediately |

The same iPhone 17 Pro needed two samples on 27.0 and one on 26.5. Any test of
this has to sample over time; a single read is a coin flip.

`env()` has no JavaScript API, so the only way to observe what a page sees is to
resolve it through a probe element and read the computed style:

```js
var p = document.createElement('div');
p.style.cssText = 'position:fixed;top:0;left:0;visibility:hidden;' +
  'padding-top:env(safe-area-inset-top,0px);' /* … */;
document.body.appendChild(p);
var cs = getComputedStyle(p);
cs.paddingTop; // "150px"
```

This is the probe from
[`EnvProbe.readEnv`](https://github.com/amoshydra/ios-webview-launcher/blob/4f48bd40f7e3f08d7cdb5219ee51a8aaf8822957/Sources/EnvProbe.swift#L12-L31),
with the comment it carries explaining why the probe element exists at all: there
is no JS API for `env()`, so reading the value out of the page is the only honest
check.

Two guards make that trustworthy:

**Prove `env()` is supported.** Read it with a fallback. If
`env(safe-area-inset-top, 77px)` returns `77px`, `env()` is unsupported and every
other number is void. Reading `0px` proves it resolved to a genuine zero. This is
what separates "the override didn't work" from "the measurement is meaningless".
The `viewport-fit=cover` half of that guard is
[`readViewportFit` in the same file](https://github.com/amoshydra/ios-webview-launcher/blob/4f48bd40f7e3f08d7cdb5219ee51a8aaf8822957/Sources/EnvProbe.swift#L33-L40).

**Capture the native value too**, so the two can be compared:

```swift
let safe = webView.safeAreaInsets           // t:150 r:40 b:180 l:40
let window = webView.window?.safeAreaInsets // t:62  r:0  b:34  l:0
```

If they diverge, the override never reached `env()`.

## Appendix: iPhone Duo

The [iPhone Duo](https://en.wikipedia.org/wiki/IPhone_Duo) is Apple's first
foldable, announced 9 September 2026 — a 5.4" outer display (1398×2034) that opens
to a 7.6" inner one (1878×2670). It ships with **iOS 27.1**, which is also the
floor the simulator enforces for the device type.

Worth a look because its safe area is a different shape from every Pro model, and
it changes shape twice over. No override set, edge-to-edge on, all three states:

| Outer, portrait | Outer, landscape | Unfolded, inner display |
| --- | --- | --- |
| <img class="shot" src="/blog/posts/webview-safe-area-inset-override/duo-outer-portrait.webp" alt="iPhone Duo folded, outer display in portrait: viewport 386 by 678, insets read 0 0 34 0" /> | <img class="shot" src="/blog/posts/webview-safe-area-inset-override/duo-outer-landscape.webp" alt="iPhone Duo folded, outer display in landscape: viewport 678 by 386, insets read 0 34 20 34" /> | <img class="shot" src="/blog/posts/webview-safe-area-inset-override/duo-inner-unfolded.webp" alt="iPhone Duo unfolded to the inner display: viewport 871 by 669, insets read 0 34 20 34" /> |
| `0 0 34 0` | `0 34 20 34` | `0 34 20 34` |

Two things fall out of that.

**No top inset, ever.** Compare the Pro models at `62 0 34 0`: the outer display
has no notch and, in the simulator, no status-bar inset, so the top is 0 in all
three states. A 150pt top override here is not restating an existing value the way
it is on a Pro — it is manufacturing an inset the hardware does not have, which is
the case where the override is most useful and hardest to test against real
hardware.

**The insets move with orientation and fold.** In portrait the whole 34pt is at
the bottom, for the home indicator. Rotate to landscape, or open the inner
display, and it splits: 34pt on each side, 20pt at the bottom. Anything that
hard-codes `env(safe-area-inset-bottom)` to size a footer is wrong in two of these
three states, and nothing in CSS warns you.

With `150 / 40 / 180 / 40` requested, the outer display reported exactly those
values back on the first sample rather than the second — the only
runtime/device in the matrix where no settling delay was observed.

## One difference worth planning for

The two overrides take different units. Android's is in physical pixels and CSS
sees it divided by `dpr`; iOS's is in points, which already are CSS pixels. If
you port a value between platforms, multiply by `dpr` on the Android side.
